3. REMAINING PILOT-READINESS GAPS
===================================

CRITICAL (blocks real use)
--------------------------

G1  No location seed data
    The Location table is empty. Horse moves require locations. The moves page, move
    creation form, and currentLocationId on horses all depend on locations existing.
    A user hitting "New Move" gets an empty location dropdown.

G2  Attachment upload is metadata-only
    HorseAttachments.tsx has a form for manually typing file paths, MIME types, and
    byte sizes. There is no <input type="file">, no multipart upload, no storage
    backend (S3/R2/local). Users cannot actually attach photos or documents.

G3  NEXTAUTH_SECRET is a hardcoded dev string
    .env has "hcmr-fleet-secret-key-minimum-32-chars-long" — fine for dev,
    unacceptable for production. No .env.production or secrets management.

G4  No error boundaries
    Zero error.tsx or global-error.tsx files. Any unhandled server error shows a
    raw Next.js error page.

G5  Neon DB credentials in .env are dev credentials
    The connection string includes plaintext password. No environment separation
    (dev/staging/prod).

SIGNIFICANT (degrades experience)
----------------------------------

G6  Duty history is read-only
    HorseDutyHistory.tsx displays history but has no form to reassign a horse's duty
    station with proper start/end dating. The only way to change duty station is via
    the horse edit form, which overwrites dutyStation but does NOT create a
    DutyAssignment record. The history audit trail is incomplete.

G7  Sidebar hides pages from troopers that they can still access
    Troopers can't see Injury Reports or Moves in the sidebar nav, but they CAN
    access /injuries and /moves directly by URL. The sidebar filtering is cosmetic,
    not a security control. The actual page-level redirect on /injuries checks
    injury_report.update which troopers lack — but troopers DO have
    injury_report.view, so they should arguably see the page.

G8  No loading/skeleton states
    Pages do server-side data fetching with no loading.tsx files. On slow Neon
    connections (cold starts), users see a blank screen until the full page renders.

G9  .env.example still references SQLite
    DATABASE_URL="file:./prisma/dev.db" — misleading for anyone setting up the project.

G10 Dead file: src/lib/auth-helpers.ts
    Exports requireRole() and getSession() but is imported by nothing. Potential confusion.

G11 No validation on horse regimental number format
    The schema requires uniqueness but the API only checks z.string().min(1). No regex
    for the HCMR-XXX pattern used in seed data.

G12 Tack and Inspections list pages are read-only
    /tack and /inspections pages display data but have no create/edit forms. You can
    only add tack items via API or within the horse detail tab. No way to create a
    new tack item from the tack list page.

G13 No pagination on any list page
    Horse list, injuries, moves, tack, inspections — all load all records. Will
    degrade with scale.

G14 No README
    No project documentation exists in the repo.


4. TOP 5 HIGHEST-PRIORITY WORKSTREAMS
=======================================

WS1  Seed locations + fix duty station reassignment flow
     Why: Without locations, horse moves are broken. Without proper duty reassignment,
     the audit trail (the whole reason we built DutyAssignment history) has a gap —
     editing a horse's station bypasses the assignment log.
     Scope: Seed script + new API logic when dutyStation changes on
     PATCH /api/horses/[id].

WS2  Real file upload for attachments
     Why: Injury photos, horse passports, and vet certificates are a core pilot
     requirement. The current metadata-only form is unusable.
     Scope: Storage backend (S3/R2/Neon blob), multipart upload API, file input
     component, presigned URL flow or direct upload.

WS3  Error boundaries + loading states
     Why: Without these, the app feels broken on any error or slow query. Neon
     free-tier cold starts can be 2-5 seconds.
     Scope: error.tsx at (app) level, loading.tsx at key route segments, toast error
     handling on client components.

WS4  Environment separation + secret management
     Why: Hardcoded dev secret, plaintext Neon password, no staging/prod split.
     Blocks any deployment beyond localhost.
     Scope: .env.example update, production env config, NEXTAUTH_SECRET rotation,
     deployment config (Vercel/similar).

WS5  Sidebar/page access alignment + trooper UX
     Why: Troopers are the most common role. Currently they can URL-access pages the
     sidebar hides, and some pages incorrectly block them (e.g., injuries list checks
     update permission but troopers only have view).
     Scope: Audit each page's redirect logic vs the RBAC matrix. Ensure sidebar
     visibility matches actual page access.

6. RISKY ASSUMPTIONS IN THE CURRENT APP
=========================================

R1  Horse edit PATCH doesn't log duty changes
    The PATCH /api/horses/[id] handler directly updates dutyStation on the horse
    record. It does NOT create a DutyAssignment. The duty history feature shows only
    assignments made at horse creation or via seed data. Any station change via edit
    silently breaks the audit trail.

R2  Soft delete assumes no cascading references
    DELETE /api/horses/[id] sets isActive: false but doesn't deactivate related
    records (feeding plans, tack allocations, rider assignments remain "active").
    Queries filtering isActive: true on horses won't return the horse, but orphaned
    related records may appear in other views.

R3  withdrawalEndDate is calculated at record creation time only
    If a vet updates withdrawalDays via PATCH, the withdrawalEndDate is NOT
    recalculated. The PATCH handler on medication-records doesn't recompute it.

R4  No rate limiting or CSRF protection on API routes
    NextAuth provides CSRF on its own routes, but custom API endpoints have no
    protection beyond JWT validation. A compromised token could be used for
    unlimited requests.

R5  All search queries are unbounded
    prisma.horse.findMany(), prisma.healthEvent.findMany(), etc. return all matching
    records. No take/skip limits except inspections (hardcoded take: 100). At
    regimental scale (~120 horses, thousands of events over years), this will cause
    slow queries.

R6  Neon free-tier cold start latency
    Neon suspends compute after inactivity. First request after idle can take 3-5
    seconds. No connection pooling configured. No loading.tsx to cover this.

R7  Suitability score is 1-5 in UI but unconstrained in schema
    RiderAssignment.suitabilityScore is Int? in Prisma with no min/max. The UI
    component shows 1-5 stars, but the API accepts any integer. Schema and UI
    disagree on range.

R8  currentLocationId can go stale
    It's only updated when a move completes. If a move is cancelled after the horse
    physically moved, the location is wrong. There's no manual override.
